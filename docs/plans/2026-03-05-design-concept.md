# Design Concept - PM x Designer 논의 결과

> 2026-03-05 | PM, Designer 합의 문서

---

## 1. 논의 배경

DOM/React 기반 디자인 에디터의 디자인 컨셉을 정의하기 위해 PM과 Designer가 논의를 진행했다. 핵심 질문: 이 에디터만의 정체성을 어떻게 시각적으로 표현할 것인가?

---

## 2. 의사결정 과정

### 2-1. PM의 초기 제안

**타겟 사용자:**

1. 프론트엔드 개발자 -- 코드를 직접 다루면서 시각적 편집의 편의를 원하는 사람
2. 디자인 엔지니어 -- 디자인 툴과 코드 사이를 오가는 하이브리드 인력
3. 스타트업/소규모 팀 -- 디자이너-개발자 핸드오프 비용을 줄이고 싶은 팀

**경쟁 제품 대비 포지셔닝:**
| 경쟁 제품 | 한계 | 우리의 차별점 |
|-----------|------|---------------|
| Figma | 벡터 기반, 디자인->코드 변환 필요 | DOM/React 네이티브 |
| Webflow | 자체 런타임 의존 | 순수 React 코드 출력 |
| Framer | 자체 프레임워크 락인 | 표준 React |
| Builder.io | 헤드리스 CMS 지향 | 코드 퍼스트 에디터 |

**PM이 제안한 4가지 디자인 원칙:**

1. 투명성 -- 사용자가 "이것이 실제 React 컴포넌트"임을 인지
2. 친숙함 -- Figma/VS Code 사용자가 바로 적응
3. 코드 의식적 디자인 -- CSS 속성 직접 노출, 컴포넌트 트리 기반 UI
4. 경량함 -- DOM 기반 특성을 살린 깔끔한 느낌

### 2-2. Designer의 피드백 (의견 차이 및 보강)

Designer는 코드베이스(App.css, Toolbar.css, PropertiesPanel.css, LayersPanel.css 등)를 직접 확인한 뒤 의견을 제시했다.

#### 의견 차이 1: "투명성" 원칙의 확장

- **PM 원안:** "투명성" -- 사용자가 React 컴포넌트임을 인지하게 하는 것
- **Designer 제안:** "투명성"을 **"코드 동시성(Code Co-presence)"**으로 확장. 단순 인지가 아니라, 코드가 항상 곁에 "같이 있는" 느낌. 별도 모드 전환이 아니라 디자인과 코드가 하나의 워크스페이스에서 공존해야 한다는 더 적극적인 개념.
- **근거:** 현재 PropertiesPanel의 Design/Prototype/Code 탭 구조가 "코드는 별도 모드"라는 인식을 줌
- **결과:** PM이 강하게 동의. "코드 동시성"으로 확정.

#### 의견 차이 2: "Craft over Feature" 원칙 추가

- **Designer 제안:** 기능 수보다 각 기능의 완성도를 우선하는 원칙 추가. 초기부터 easing, 스냅, 피드백 디테일을 챙겨야 한다.
- **근거:** 현재 코드베이스에 유니코드 문자(↖, ⬜) 아이콘, 이모지(🔒, 👁) 등 프로토타입 수준 UI가 남아있음
- **결과:** PM 동의. 5번째 원칙으로 추가 확정.

#### 의견 일치: 비주얼 톤

**테마 -- 하이브리드 접근:**

- Designer가 "라이트 퍼스트 + 코드 영역 다크" 하이브리드 제안
- 전체 UI는 라이트 (디자인 도구 성격), 코드 영역만 다크 (VS Code 경험 일치)
- PM 동의: Monaco 에디터가 이미 별도 영역으로 분리되어 있어 자연스러움

**액센트 컬러 -- Warm Amber로 차별화:**

- 초기 제안은 Indigo `#6366F1`이었으나, Tailwind indigo-500 그대로라는 피드백을 받아 재작업
- Designer가 색상환에서 경쟁 도구들(Figma, Framer, Webflow, VS Code)이 점유한 Blue-Purple(210-270) 대역을 분석, 유일하게 빈 Warm Amber(25-40) 대역을 제안
- **Main: `#E08A2D` (Warm Amber)** -- "코드를 직접 손으로 빚는다"는 공방 메타포. 차가운 Blue 계열 도구들과 색온도로 즉시 차별화
- **Sub: `#2D5C7B` (Deep Slate Teal)** -- 터미널/IDE 배경에서 오는 "코드 그 자체" 색감
- PM 동의: 방향은 좋으나 접근성 검증 필요 → Designer가 WCAG AA 검증 완료 후 확정

**"코드가 곧 디자인"의 UI 표현 -- Designer가 제시한 구체 아이디어:**

1. 속성 패널 듀얼 뷰 -- Design/Code를 탭이 아닌 split view로
2. 캔버스 인라인 코드 힌트 -- 호버 시 태그/컴포넌트명 뱃지 표시
3. 레이어 패널 태그 표기 강화 -- `<div>`, `<span>` 형식
4. 하단 접이식 코드 에디터 패널 -- VS Code 터미널 패널 방식

**"Figma 클론" 우려:**

- Designer가 "친숙함" 원칙이 Figma 클론으로 흐를 수 있다고 경고
- 합의: 레이아웃 뼈대는 업계 표준을 따르되, 3가지에서 확실히 차별화
  1. 하이브리드 라이트/다크 테마
  2. Warm Amber 액센트
  3. 코드 동시성 UI

### 2-3. PM의 우선순위 정리

PM이 코드베이스 현실을 고려하여 3단계 우선순위를 제안. Designer 동의. 이 단계에서 의견 불일치 없음.

### 2-4. Designer의 세부 사양 확정

Designer가 구현에 필요한 구체 수치(컬러 팔레트, 코드-매핑, CSS 구조)를 확정. PM 동의.

## 3. 확정된 디자인 컨셉

### 3-1. 핵심 원칙

1. **코드 동시성 (Code Co-presence)** -- 코드가 별도 모드가 아니라 디자인과 항상 공존
2. **친숙함** -- Figma/VS Code 사용자가 바로 적응할 수 있는 UI 패턴
3. **코드 의식적 디자인** -- CSS 속성 직접 노출, 컴포넌트 트리 기반 레이어 패널
4. **경량함** -- DOM 기반 특성을 살린 깔끔하고 가벼운 느낌
5. **Craft over Feature** -- 기능 수보다 각 기능의 인터랙션 완성도 우선

### 3-2. 비주얼 시스템

| 테마        | 라이트 퍼스트 + 코드 영역 다크 하이브리드 |
